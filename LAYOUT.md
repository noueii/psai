# Layout: where things go

psai is the framework; content lives in stacks (ADR 0011). This map says where each kind of file goes **inside a stack** (one you install, one you author with `psai new-stack`, or your overlay `nostack`), what the **framework** ships, and how a machine's **home** is laid out. `customize-harness`, `capture-knowledge` and the retro file everything by it. `psai check <stack>` fails on any file under `workflows/ steps/ roles/ guides/ templates/ knowledge/ my-skills/` whose path doesn't match the **Goes in** column (`<x>` matches one path segment, `/**` anything below).

## Inside a stack
| You're adding | Goes in | Format |
|---|---|---|
| the stack's manifest | `stack.yaml` | schemas/stack.schema.json: name, version, description, psai range, requires, exports, routing, models |
| a workflow | `workflows/<name>.yaml` | state machine, see the stack's workflows/README.md |
| its simulator cases | `workflows/<name>.cases.yaml` | scripted outcomes and the expected path |
| a route to a workflow | `workflows/ROUTING.yaml` | a branch of the decision tree (created with the first workflow); `ROUTING.cases.yaml` for its cases |
| workflow diagrams | `workflows/GRAPHS.md` | generated by `psai graph <stack> --update-readme` |
| a step | `steps/<name>.md` | frontmatter `read:`, optional `skills:` + prose |
| a role | `roles/<name>.md` | frontmatter `may_change:`, `read:`, optional `skills:` and `model:` + prose |
| the stack's own skill | `my-skills/<name>/SKILL.md` and its files `my-skills/<name>/**` | flat; `name` = folder, prefixed with the stack's name; quoted `description` with "Use when ..." |
| someone else's skill | `skills.yaml` | a pinned entry (name, source, path, ref) or an `ignore:` name |
| a skill for one repo only | `<repo>/.agents/skills/<name>/SKILL.md`, linked from `<repo>/.claude/skills/<name>` | same as my-skills; list it as optional |
| a role's knowledge | `knowledge/roles/<role>/INDEX.md` | index; created with the role |
| a rule for one kind of work | `guides/<name>.md` | prescriptive prose, attached with `read:` |
| an output format | `templates/<name>.md` | the format, then a filled-in example |
| the stack's always-on rules | `instructions/stack.md` | a few bullets, ≤ 60 words in the nudge |
| a promoted fact | `knowledge/facts/<topic>.md` | prose with sources |
| a promoted decision | `knowledge/decisions/<date>-<slug>.md` | Decision / Why / Source |
| the knowledge index | `knowledge/INDEX.md` | one line per file |
| an eval scenario | `evals/scenarios/<name>.yaml` | see psai's evals/scenarios/README.md; `psai eval <stack>` runs them |
| **your overlay only:** a rule for every task | `instructions/owner.md` | short bullets; injected live into every session |
| **your overlay only:** a finding during a task | `knowledge/inbox.md` or `knowledge/roles/<role>/inbox.md` | dated entry, see capture-knowledge |
| **your overlay only:** your knowledge about another stack's role | `knowledge/<stack>/roles/<role>/INDEX.md` and `knowledge/<stack>/roles/<role>/inbox.md` | index and inbox; read after the stack's own |
| **your overlay only:** your change to another stack's file | `overrides/<stack>/<path>` | `psai stack override <stack>:<path>`; `.base.yaml` records what it replaced |
| **your overlay only:** the stacks on this machine | `stacks.yaml` | written by `psai stack add|remove|update` |

Folder READMEs (`<folder>/README.md`) describe each folder and are always allowed. A stack holds content only: adding one never runs its code.

## The framework (psai itself)
`skills/`, `plugins/`, `scripts/`, `migrations/`, `schemas/`, `template/` (what `psai new-stack` copies), `install.sh`, `VERSION`, `evals/` (psai's own scenarios, graders and neutral test fixtures, including the test stacks in `evals/fixtures/stacks/`), `docs/`, `.claude-plugin/`, `instructions/global.md`, this map and every `README.md`. It ships no content folder and no stack: `scripts/check.sh --upstream` fails if it does.

## The home (one machine; ADR 0011)
`~/.psai` (`$PSAI_HOME` moves it) is a folder that install.sh sets up:
- `framework/`: a link to the psai clone install.sh ran from;
- `overlay/`: your stack `nostack`, a git repo created on install. It holds `stack.yaml`, `stacks.yaml` (the installed stacks), your own content (`nostack:...`) and the rows marked **your overlay only** above: `instructions/owner.md`, knowledge and every inbox, overrides;
- `overlay/overrides/<stack>/<path>`: your replacement for one installed stack's file (`psai stack override <stack>:<path>`), found by name instead of the original; `.base.yaml` there records what it replaced, so `psai stack update` reports an original that changed. Cases next to an overridden workflow are your own. Knowledge and a stack's `stack.yaml` are never overridden;
- `stacks/<name>/`: each installed stack;
- `state/`: this machine's local state (`$PSAI_STATE` moves it): the session ledger, the stage worktree where changes wait for the retro's or sync's PR, retro reports, the install and migration records, the drift baseline, and `skills-cache/<stack>/` with the fetched `skills.yaml` entries. It is never shared.

A home that is still a link to a fork clone is converted on the next install (migration 0002): your files move into `overlay/`, `.state/` into `state/`, and the clone's own files are left alone.

Precedence, most specific wins: your overlay's override of a stack's file > the stack's file; the step or role and its `read:` files > `instructions/owner.md` > a stack's `instructions/stack.md` > `instructions/global.md`. psai has no per-repo layer: a rule for one repo goes in that repo's own AGENTS.md or docs (ADR 0011, Q2). Content is found by name with `psai resolve`, never by a hard-coded path.
